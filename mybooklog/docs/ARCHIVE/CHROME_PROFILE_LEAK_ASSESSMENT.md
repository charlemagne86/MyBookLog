# Chrome Profile Leak — Compromised Data Assessment

**Subject:** Finding SEC-1 from the MyBookLog analysis — Chrome browser profile committed and pushed to the public GitHub repo `charlemagne86/MyBookLog`.
**Date:** 2026-07-16
**Method:** Extracted the committed database blobs from git (`HEAD` and all-history), inspected each SQLite table directly (Python `sqlite3`, read-only). Verified only one distinct version of each file exists across the entire public history.

---

## Bottom line (this corrects the original report)

**No real accounts, credentials, cookies, passwords, payment methods, or personal browsing data were compromised.**

The committed `mybooklog/.dart_tool/chrome-device/` folder is **not a personal browser profile.** It is the **ephemeral, throwaway Chrome profile that the Flutter tooling auto-creates** whenever you run `flutter run -d chrome`. It was never signed into a Google account and was never used for personal browsing. Every sensitive table in it is **empty**.

The original PROJECT_ANALYSIS.md advice to "sign out of Google everywhere and treat synced credentials as compromised" was **based on the alarming file *names* (`Cookies`, `Account Web Data`, `Login Data`) rather than their contents, and overstated the risk.** The correct action is ordinary cleanup (purge the files from history), not credential rotation or session invalidation.

The one thing that remains true and worth doing: these files are junk that should never have been committed, and they still bloat the repo and leak trivial machine metadata. Remove them (see [Cleanup](#cleanup)).

## Why this happened

When you run a Flutter web app with `flutter run -d chrome`, the tool launches Chrome with a **dedicated, isolated user-data directory** at `mybooklog/.dart_tool/chrome-device/` so it doesn't touch your real Chrome profile. That directory is created fresh, populated only with Chrome's default scaffolding (default search engines, empty databases), and used solely to load `localhost:<port>`. It was then accidentally committed because `.dart_tool/` was added to `.gitignore` only *after* these files had already been tracked.

**Commits involved (both on the public history):**
- `c64bfa8` "Done with User sign-up and login" — added the profile.
- `d4f21e1` "Second pass at themeing" — touched it again.

Across all of history there is exactly **one** version of each database blob, and it is the empty one analyzed above — so nothing populated ever existed in a prior commit either.

## Cleanup

No credential rotation, password changes, or Google sign-outs are required. Treat this purely as repo hygiene:

1. Untrack the folder (and the other build junk):
   ```bash
   cd /home/charlie/Repositories/MyBookLog
   git rm -r --cached mybooklog/.dart_tool mybooklog/build mybooklog/android/local.properties
   git commit -m "Remove build artifacts and Flutter Chrome dev-profile from tracking"
   ```
   `.gitignore` already lists `.dart_tool/`, so it will stay untracked going forward.

2. (Optional, for a clean history) purge it from all past commits so the ~170 junk files stop shipping in every clone:
   ```bash
   git filter-repo --path mybooklog/.dart_tool --path mybooklog/build \
                   --path mybooklog/android/local.properties --invert-paths
   git push origin --force --all && git push origin --force --tags
   ```
   This is a nice-to-have for repo size/cleanliness — **not** a security necessity, since the contents are empty.
